# SQL Security Policy & Query Execution Standards

## 1. Overview

This document specifies the formal security policy governing all SQL query parsing, validation, and execution within the AI Business Intelligence Agent.

Under no circumstances is raw, untrusted SQL generated by Large Language Models (LLMs) or external clients executed directly against any database. Every query must satisfy the deterministic policies detailed herein.

---

## 2. Policy Enforcement Rules

### 2.1 Single Statement Enforcement
- The input SQL string must resolve to **exactly one statement**.
- Stacked queries (e.g. `SELECT 1; DROP TABLE users;`) and embedded semicolons are rejected during AST parsing.

### 2.2 Root Expression Restriction
- The root AST expression must be an instance of `sqlglot.exp.Select` or `sqlglot.exp.Union`.
- The following statements and AST expressions are strictly forbidden:
  - **DML**: `Insert`, `Update`, `Delete`, `Merge`
  - **DDL**: `Create`, `Alter`, `Drop`
  - **TCL / Admin**: `Transaction`, `Commit`, `Rollback`, `Set`, `Show`, `Describe`, `Analyze`, `Lock`, `Into`
  - **Database Commands**: `Command`, `Pragma`, `Grant`, `Revoke`, `Kill`

### 2.3 Strict Table Allowlists
- Every table referenced anywhere in the query—including joins, subqueries, and Common Table Expressions (CTEs)—must exist in the session's permitted table set.
- CTE aliases defined in `WITH` clauses are tracked and permitted within the scope of the query, but the underlying data source tables queried by the CTE must be allowlisted.

### 2.4 System Catalog & Metadata Protection
The following schemas and system tables are strictly prohibited from query plans:
- **Schemas**: `pg_catalog`, `information_schema`, `sys`, `sqlite_master`, `sqlite_temp_master`, `mysql`
- **Tables**: `pg_shadow`, `pg_authid`, `pg_user`, `pg_database`, `pg_tables`, `sqlite_master`, `sqlite_schema`

### 2.5 Prohibited SQL Functions
Calls to the following categories of database functions are blocked by policy:
- **File System Access**: `pg_read_file`, `pg_read_binary_file`, `pg_write_file`, `lo_import`, `lo_export`
- **Execution & Delays**: `pg_sleep`, `pg_sleep_for`, `pg_sleep_until`
- **Remote / Network Connections**: `dblink`, `dblink_connect`, `dblink_exec`, `pg_background_launch`
- **Configuration Modifications**: `set_config`, `current_setting` (in user queries)
- **Data Exfiltration Vectors**: `query_to_xml`, `table_to_xml`, `query_to_xml_and_xmlschema`, `cursor_to_xml`

## 3. Database-Level Enforcement

In addition to AST validation, database connectors enforce least-privilege policies at the connection level:

### 3.1 PostgreSQL Connector
1. **Unprivileged Role**: The application connects using `bi_analytics_readonly`, which has `REVOKE ALL ON ALL TABLES` by default and only explicit `GRANT SELECT` on approved tenant tables.
2. **Read-Only Transactions**: Transactions are opened with `readonly=True`. The server rejects write statements even if the user attempts to bypass AST validation.
3. **Session Variables & RLS**:
   ```sql
   SET LOCAL app.current_tenant_id = '...';
   SET LOCAL app.current_user_id = '...';
   ```
   PostgreSQL RLS policies restrict visible rows to the matching `org_id`.
4. **Resource Ceilings**:
   - `statement_timeout = 15000` (15 seconds)
   - `lock_timeout = 5000` (5 seconds)
   - `idle_in_transaction_session_timeout = 10000` (10 seconds)
   - `work_mem = '32MB'`
   - Maximum response byte limit: 10 MB
   - Maximum row limit: 5,000 rows
5. **Connection Hygiene**:
   Upon releasing a connection back to the asyncpg pool:
   ```sql
   RESET ALL;
   DISCARD TEMP;
   ```

### 3.2 SQLite Connector (CSV & Excel Ingestion)
1. **Engine Authorizer Callback**:
   A native SQLite authorizer callback is registered on the connection using `conn.set_authorizer(sqlite_authorizer)`.
   - Permitted actions: `SQLITE_SELECT`, `SQLITE_READ`, `SQLITE_FUNCTION`
   - Denied actions: `SQLITE_INSERT`, `SQLITE_UPDATE`, `SQLITE_DELETE`, `SQLITE_PRAGMA`, `SQLITE_CREATE_*`, `SQLITE_DROP_*`, `SQLITE_ALTER_*`, `SQLITE_ATTACH`, `SQLITE_DETACH`
2. **Size Enforcement**: Query result payloads cannot exceed 10 MB or 5,000 rows.

---

## 4. Audit Logging & Non-Repudiation

Whenever a query fails or is rejected:
1. No connection is opened to the database.
2. An `AuditEvent` record is committed with:
   - `action`: `query.rejected`
   - `actor_id`: authenticated user ID
   - `org_id`: authenticated organization ID
   - `details`: exact validation failure reason, SQL query hash, sanitized error message.
